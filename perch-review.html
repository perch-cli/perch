Perch — Deep Code Review

Security, correctness, simplification, dependency hygiene, and test quality
Scope: ~6.7k lines src/, ~5k lines tests/ (edition 2024, Rust 1.97.1) Method: four parallel review passes, every finding re-verified against source Date: 2026-08-06

Perch is a small, unusually careful CLI: it swaps Claude Code OAuth credentials between accounts using the same keychain / credential-file stores and directory locks Claude Code itself uses. The design is documented to a rare standard (24 ADRs, a domain glossary), and the review confirmed that most of the hard problems — argv secrecy, capture-before-write ordering, PID-recycling corroboration, format-preserving JSON edits — are handled correctly. The findings below are the exceptions. The recurring theme is a double standard: the machinery Perch built to protect files it does not own (atomic writes, 0600 creation, read-back guards) is not consistently applied to its own state, nor to every path that writes a live credential.

High severity

H1 High security Every switch rewrites ~/.claude.json at the process umask, discarding its mode

src/host/mod.rs:270-286 · src/host/real.rs:177-183 · src/switch.rs:246
Cause

patch_identity writes the identity file through host::write_atomically, which creates its temp file with plain std::fs::write. That gives the new file 0o666 & ~umask (0644 on a normal umask; 0666 under the umask 000/002 some CI and container images use), then renames it over ~/.claude.json. Whatever mode the original file had is discarded on the very first switch, permanently. Perch already knows the correct pattern — write_private_file is documented as creating a file 0600 "even where something looser was already there" — that reasoning was just never applied to .claude.json.

Explanation

.claude.json is not innocuous: this repo's own doc (src/json.rs:5-7) describes it as holding "project history, MCP configuration and settings", and MCP server entries routinely carry API keys in their env block. No race is required — the exposure is a stable file mode.

  before first switch          after first switch
  ┌───────────────────┐        ┌────────────────────────────┐
  │ ~/.claude.json     │  switch │ ~/.claude.json  mode 0644  │  ← world-readable
  │   mode 0600 (safe) │ ─────► │   (temp made at umask,     │
  │                    │        │    then renamed over it)   │
  └───────────────────┘        └────────────────────────────┘
                                 + every .claude.json.perch-tmp
                                   was world-readable too
  attacker (any other uid on the box: build agent, shared /home,
  container) → `cat ~/.claude.json` → harvests every MCP secret
Solution

Add a write_atomically_preserving_mode: stat the target, create the temp with OpenOptions::mode() set to the target's existing mode (default 0600 when the target doesn't exist yet), and rename. On non-unix this is a no-op, as elsewhere.

Effect

Costs one extra stat per switch. Closes a permanent, no-race, cross-user credential leak that ordinary use opens on the first switch. One decision to make: a fresh .claude.json created 0600 is stricter than Claude Code's own default, so a user diffing modes may notice.

H2 High bug remove updates the active pointer after the destructive step, poisoning the next switch on failure

src/commands/remove.rs:99-119
Cause

The order is: land_on(successor) (which makes the successor's credential live via switch::make_live), then delete_the_credential_and_its_profile(account), and only then is registry.active set to the successor and saved. If the delete fails (a locked/denied keychain returning non-44, or account.store() failing), the command aborts — but on disk active still names the removed account while the live credential is already the successor's.

Explanation

Being active "is a fact about which Credential is in the Default Profile, not a wish" (the design's own words). switch::perform goes to great lengths to record incoming_is_live even on failure; remove breaks that invariant, and the corrupted pointer feeds the capture-before-write logic that ADR 0006 is built to protect.

  remove A (active), successor B:

   1. make_live(B)      ✔  live credential = B
   2. delete A's cred   ✘  keychain denies → command aborts
   3. save active=B        never reached

  on disk now:  active = A     live credential = B   ← disagree

  user then runs `perch switch C` (the error said A "is still held"):
     outgoing := active_account() = A
     capture(): copies the LIVE credential (B's!) into A's profile
     → A's own captured credential is destroyed (unrecoverable, ADR 0006)
     → A is now quarantine-bound; A's profile now holds B's credential
Solution

Set registry.active = Some(successor) and save immediately after land_on succeeds, before deleting anything. (This does not violate ADR 0024's "registry written last" rule — that rule is about not dropping the account row before its credential is gone.) Separately, give make_live an incoming_is_live-style result so partial-failure notes stop asserting things that are no longer true.

Effect

Any failure mid-removal leaves a coherent machine — active names the account whose credential is actually live — so re-running remove or reaching for switch is safe instead of destructive.

H3 High bug · security No cross-process lock on the registry; a stale copy held across a login clobbers concurrent writes

src/registry.rs:739-821 · src/commands/add.rs:35-74
Cause

Every command is load → mutate in memory → save with no Perch-owned mutual exclusion (the locks in lock.rs are Claude Code's credential locks, taken only during a switch). add and relogin deliberately keep the session usable across a minutes-long interactive browser login, holding their in-memory registry the whole time and writing it back wholesale at the end. Running several accounts in parallel terminals is an explicitly supported workflow (ADR 0010).

Explanation
  terminal A: perch add           terminal B: perch switch Y
  ──────────────────────          ──────────────────────────
  load registry (active=X)
  open browser ...........        capture X's live cred → X's profile
  (user takes 2 min)              make Y live; save active=Y
  login done
  save STALE copy:
    + account Z, active=X   ◄──── silently reverts B's active=Y

  next bare `perch switch`: outgoing=X but live cred=Y
    → capture writes Y's cred over X's good copy → X destroyed

The same gap drops a status --refresh quarantine flag, loses a config edit, and orphans add's freshly created profile with no registry row naming it.

Solution

Take an exclusive Perch lock (a lock directory under $PERCH_HOME, reusing the existing create_dir_exclusive mkdir primitive) around each load → mutate → save. For add/relogin, hold it only around the final re-load + save after the login returns, re-validating names and active — never across the browser round trip.

Effect

Concurrent Perch commands can no longer revert active or lose each other's writes; the capture invariant survives interleavings. Introduces a short contention window (keep it off the login wait, or every command blocks behind an in-progress add).

H4 High bug · security add refuses only an exact-email duplicate, so slug collisions overwrite a held credential

src/commands/add.rs:118-136 · src/registry.rs:729-736
Cause

refuse_an_account_perch_already_holds checks registry.account(&identity.email) — an exact, case-sensitive match. But the profile directory and keychain namespace are derived from slug(email), which lowercases and maps every non-alphanumeric to -. So user+work@gmail.com, user.work@gmail.com, and User-Work@gmail.com all resolve to one profile. remove and switch both guard against shared slugs (registry::same_profile); add is the one that's allowed to create the collision destructively.

Explanation

Plus-addressing on one inbox is exactly how this tool's audience holds several Anthropic accounts. Adding user+work@gmail.com when user.work@gmail.com is held passes the exact-match refusal, then store_credential's supersede logic replaces the existing account's credential and deletes its other-store copy — the first account's refresh token is destroyed with no warning, and one of the two rows is now permanently quarantine-bound. A case-variant login (which switch/relogin treat as possible, comparing with eq_ignore_ascii_case) instead creates a second registry row over the same profile, so cycling ranks one physical account twice.

Solution

In the refusal, reject when any held account satisfies registry::same_profile(existing.email(), identity.email) (which also covers case variants), naming the sharer and pointing at relogin. A hash suffix on the slug would additionally eliminate the collision class entirely.

Effect

A colliding login is refused after authentication (nothing written) instead of silently destroying a held credential. The check is one predicate change.

H5 High security · bug An all-non-alphanumeric email slugs to "", collapsing the profile path onto the profiles root — remove then deletes everything

src/registry.rs:706-736 · src/commands/remove.rs:318 · src/probe.rs:506-515
Cause

slug() is a good traversal defence (../ → ---) but it can return the empty string after trim_matches('-'). Nothing validates the email: it comes from oauthAccount.emailAddress (which read_identity only requires to be present) or a hand-edited/migrated registry.json (load does no per-account validation).

  slug("@")                    == ""
  profiles_dir.join("")        == ~/.perch/profiles/          ← the ROOT
  store.config_dir             == ~/.perch/profiles/
  credentials_file             == ~/.perch/profiles/.credentials.json
Explanation

In remove, after the (single-account) sharer guard passes, host.remove_dir_all(&store.config_dir) is called on ~/.perch/profiles — every profile directory of every account. On Linux/Windows, where the plaintext store is primary, that is every credential Perch holds. The same collapse also makes add/adopt write into the profiles root and derive the keychain service from it, breaking the per-profile namespace ADR 0001 relies on. Likelihood is low (the email normally comes from Claude Code's own login), which is why it's High rather than Critical — but the blast radius is total data loss.

Solution

In profile_dir_for, reject an email whose slug is empty (PerchError::Invalid) and assert the derived directory is a strict child of profiles_dir. Validate emailAddress at adoption/read time.

Effect

A degenerate email becomes a clean refusal instead of a machine-wide delete. An account already recorded with such an email becomes unusable rather than dangerous (needs a migration/manual edit — the right direction).

Medium severity

M1 Medium bug · security · simplify registry::save is a truncating write with no atomicity

src/registry.rs:810-821 · src/host/real.rs:177-183

Found independently by the bug, security, and simplification passes.

Cause

registry::write calls host.write_file → bare std::fs::write (truncate, then write). host::write_atomically (write-beside + rename) exists three lines away in the same abstraction and is used for .claude.json precisely because a half-written file "would cost them all of that" — but it was never applied to Perch's own single source of truth.

Explanation

registry.json holds the account list, active pointer, aliases, groups, quarantine reasons, and the utilization cache. status is advertised for shell prompts ("it may run several times a minute"), so a reader can hit a mid-write truncated file → serde_json::from_str fails → PerchError::Malformed from adopt::ensure_adopted, which every command calls first. A crash/SIGKILL mid-write (laptop lid during status --refresh's save) leaves the file truncated permanently, and there is no repair path in the codebase — every command fails until the file is hand-edited.

Solution

Route registry::write through host::write_atomically (and, per M7, its private-mode variant). One-line change.

Effect

Readers always see the old or new registry; a crash can no longer corrupt Perch's entire state. Removes the last torn-write hazard in the state layer.

M2 Medium security An abandoned login leaves a live refresh token orphaned forever

src/login.rs:39-66 · src/registry.rs:716-720
Cause

Cleanup (profile::discard) only runs if exec_interactive returns normally. There is no signal handling anywhere in the crate and no startup sweep of ~/.perch/pending. Ctrl-C delivers SIGINT to the whole foreground group, so Perch dies without unwinding — and the documented flow ("quit Claude Code when the login is done") makes abandoning a login expected.

Explanation

What's left behind is a complete, live credential: off-macOS a ~/.perch/pending/login-<millis>/.credentials.json; on macOS a keychain item under a service derived from sha256(pending dir). Because the directory is keyed on timestamp_millis(), every abandoned login creates a new orphan, and nothing in Perch ever re-derives, lists, or deletes them. The keychain orphans are wholly invisible and hold refresh tokens valid until Anthropic rotates them — a slow accumulation of working credentials for accounts the user believes they never added.

Solution

Sweep ~/.perch/pending/* at the start of every command: for each entry older than a few minutes, derive its Store and profile::discard it. (The age bound protects a concurrent in-flight add.) Optionally add a SIGINT/SIGTERM handler too, but the sweep alone closes the hole.

Effect

Orphaned credentials are reaped within one subsequent command instead of living forever. Cost: a directory listing and up to N keychain deletes per command, bounded by the age filter.

M3 Medium security Liveness is checked before the locks and never re-checked under them (switch path)

src/switch.rs:160-201, 95-104, 135-143
Cause

prepare runs refuse_if_live and reads the incoming credential outside any lock; the lock is taken afterwards, and the check is never repeated inside it. The justification — "a Profile that nothing is running against does not change underneath Perch" — is the classic time-of-check argument: the refusal established that a moment ago, not for the duration of the write. Lock acquisition can take seconds (lock::take sleeps up to 4×1000 ms).

Explanation

observe.rs gets this right and shows the intended pattern — it re-runs refuse_if_live inside lock::under ("both of the questions asked before the locks were taken, asked again now that nothing can change the answer"). switch::perform and switch::make_live don't. A claude started during the lock wait is invisible to the switch, and the switch replaces the credential that session is holding — the mid-task logout ADR 0005 exists to prevent. It's worse inside remove's land_on, where the credential being replaced belongs to an account about to be deleted.

  switch: check_live(A) ─── (gap: up to ~4s of lock wait) ─── write cred
                    ▲                    │
              says "not live"     `claude` starts here → now live,
                                   but switch never looks again → clobbered
Solution

Move the refuse_if_live calls (and the incoming-credential read) inside the lock::under closure, matching observe.rs.

Effect

Lock held marginally longer; the TOCTOU window on the credential swap closes. Cheap next to the correctness gain.

M4 Medium bug A failed final make-live in relogin lets the next switch destroy the freshly repaired credential

src/commands/relogin.rs:86-96, 171-180 · src/switch.rs:204-219
Cause

After a successful repair, the fresh credential is in the account's own profile and the registry is saved; then make_it_live runs, best-effort. If it fails (locked keychain, .claude.json write failure), the state is active = account but the live credential is still the old, broken one. The note says "run perch relogin again" — but if the user instead runs perch switch other (equally natural), capture copies the broken live credential over the fresh one in the account's profile.

Explanation

ADR 0023 names this exact hazard ("the Capture would write the broken copy over the fresh one") but only defends against it inside relogin, not on the switch that follows a failed make_it_live. The repaired account returns to quarantine and the browser round trip is wasted.

Solution

Either (a) on make_it_live failure set registry.active = None (with an explaining note) so the next switch has no outgoing to capture into, or (b) make capture skip-with-note when the live identity file names an account other than outgoing — a coherence check the codebase already has the pieces for (already_landed).

Effect

A half-finished repair can no longer be undone by the very command a user reaches for next.

M5 Medium bug status --refresh can quarantine the active account off an unconfirmed foreign credential (ADR 0019)

src/observe.rs:191-206, 322, 425-433
Cause

For the active account, holding() selects the Default store — the one "Perch is not the only thing that writes". The code then renews and records renewal-terminal outcomes (NoRefreshToken, RenewalRejected, RotationLost) before confirm() checks whose token it actually was:

let asked = holding(host, registry, account)?;      // active → Default store
let token = usable_token(host, &asked, &version)?;   // may renew, may Quarantine
confirm(host, &token, account)?;                     // ownership checked only AFTER
Explanation

Concretely: the user ran claude and logged in directly as a different account; that login later dies. status --refresh reads the foreign live credential, fails to renew it, and quarantines the account Perch believes is active — whose own profile still holds a good credential. ADR 0019 says a figure is recorded only against the account it was read for, and that a token belonging to someone else "records nothing… names the account the token really belongs to and stops there." A quarantine is a recording, made here without that check.

Solution

When asked is not the account's own profile, never write a terminal quarantine off it — downgrade renewal-terminal outcomes to a non-terminal Failed, or confirm ownership before recording. Quarantine only off the account's own profile, where the credential is unambiguously theirs.

Effect

A terminal, user-visible quarantine is only ever recorded against the account it's actually true of.

M6 Medium bug credentials::read collapses a fallback-store error into "logged out"

src/credentials.rs:77-85
Cause

When the primary store holds nothing and the fallback store errors (e.g. .credentials.json exists but is unreadable — permissions), the final match arm is _ => otherwise.map(|_| None), returning Ok(None) — indistinguishable from "no credential anywhere". The primary's error is preserved, but a fallback error is silently swallowed into a no-login answer.

Explanation

"Logged out" is not benign here: in observe::credential_in it triggers a Quarantine (NoCredential) — a terminal state — for an account whose profile file is merely temporarily unreadable, and it drives adoption refusals elsewhere.

Solution

Distinguish "fallback holds nothing" (Ok(None)) from "fallback errored" — on a genuine read error with the primary empty, surface a non-terminal failure rather than None. At minimum pin the intended behaviour with a test either way (the branch is currently undecided and untested).

Effect

A transient unreadable file stops being promoted to a permanent quarantine.

M7 Medium security registry.json and ~/.perch are world-readable

src/registry.rs:810-821
Cause

registry::write uses host.create_dir_all (mode 0755) and host.write_file (mode 0644), never the create_private_dir_all / write_private_file variants that the credential paths correctly use. The profile directories themselves are 0700 — this gap is specific to Perch's own metadata file.

Explanation

The registry holds no credential, but it does hold every account's email, organization name, plan, alias, group membership, quarantine reasons, and utilization history — a full picture of the user's Anthropic relationships, readable by any other local user.

Solution

Write the registry with write_private_file and create ~/.perch with create_private_dir_all (this also delivers M1's atomicity if the private writer is the atomic one).

Effect

New installs get 0600/0700. An existing ~/.perch keeps its 0755 (the private-dir helper is documented as not a chmod in disguise), so upgraders need a one-time tighten.

M8 Medium bug Target resolution is case-sensitive while naming rules are case-insensitive

src/target.rs:91-109 · src/registry.rs:485-493, 554-559
Cause

target::matched resolves aliases/emails/groups with exact BTreeMap/== lookups, but the registry's own name rules are explicitly case-insensitive ("work and Work reaching different Accounts is the ambiguity this exists to prevent — even though a lookup could tell them apart").

Explanation

perch group add Work then perch switch work → "nothing is called work, did you mean Work?" — while config set work …, group move x work, group remove work, and alias work --unset all accept the lowercase spelling. Emails diverge the same way (remove Someone@… misses someone@… save for the suggestion, while already_landed compares case-insensitively). Every command should accept the same spelling.

Solution

Resolve aliases via declared_alias, groups via declared_group, and accounts via a case-insensitive email scan (uniqueness is already guaranteed by the shared namespace + slug rules once H4 is fixed).

Effect

No command refuses a name another command accepts.

Low severity

L1 Low security The credential reaches argv on the oversize-write fallback

src/host/real.rs:323-339 · src/keychain.rs:8-11
Cause

The module header promises "a Credential never reaches argv", and the normal path honours it via security -i on stdin. But when the -i command line would exceed ~3840 bytes, the fallback puts the hex-encoded secret directly in argv. Hex is an encoding, not a protection — anything that can read the process table recovers it with xxd -r -p.

Explanation

Reachable once a credential block grows past ~1.9 KB (extra scopes/org fields). Bounded to same-user and root on macOS (KERN_PROCARGS2 is uid-restricted), which is why it's Low, not High — but it silently breaks the exact invariant the file documents.

Solution

Chunk the -i input to stay on stdin, or at minimum host.note() when the argv path is taken so the exposure isn't silent. Avoid a temp file (re-introduces a secret on disk, against ADR 0020).

Effect

Restores the argv-secrecy guarantee for large credentials, or makes the one exception visible.

L2 Low security A newline in $USER injects a second sub-command into security -i

src/keychain.rs:80-104 · src/probe.rs:353-364
Cause

quote() escapes backslashes and quotes but not newlines, and security -i is line-oriented (one sub-command per line). account is $USER/$USERNAME verbatim, with no validation. A value like x\ndelete-generic-password -s "Claude Code-credentials" becomes two commands — and since -i reports a failed sub-command on stderr while still exiting 0, an injected command that succeeds is silent.

Explanation

Low because it needs control of Perch's environment, and anyone with that has stronger levers (PATH, PERCH_CLAUDE_BIN). But quote is documented as if it made the value inert — the kind of false assumption that gets reused later on genuinely attacker-supplied input.

Solution

Reject a service/account containing a control character in add_command_line, naming the variable. One line, no behaviour change for real login names.

Effect

The stdin protocol becomes injection-proof and the "inert" claim becomes true.

L3 Low security · bug indent_to_match mixes byte and char offsets and panics on non-ASCII indentation

src/json.rs:141-163
Cause

own is a byte indent width (line.len() - line.trim_start().len()) taken as the min over lines, then used to byte-slice every other line: &line[own.min(line.len())..]. trim_start trims Unicode whitespace, so a block indented with mixed multi-byte whitespace (e.g. U+00A0 then U+2028) yields an own that slices another line mid-char → panic. The sibling function indentation_of_the_line counts chars() for the same concept — the tell that the two disagree.

Explanation

The re-indented block is read verbatim from a profile's .claude.json (a file Perch doesn't own). Impact is a panic, not compromise — but it fires inside patch_identity, after the incoming credential is already live, leaving the machine acting as one account while displaying another and printing a "this is a bug" panic instead of the recovery instructions live_but_unnamed was written to give.

Solution

Compute and strip the common indent in chars (or via str::strip_prefix on the shared prefix), never a raw byte slice.

Effect

No panic on non-ASCII indentation; the interrupted-switch recovery path stays reachable.

L4 Low security write_atomically follows a symlink at its predictable temp path

src/host/mod.rs:275 · src/host/real.rs:504-518
Cause

The atomic path writes the temp file with std::fs::write, which follows a symlink at <path>.perch-tmp (a fixed, unrandomised suffix). The private-file writer deliberately remove_files first and uses create_new(true); the atomic writer does neither.

Explanation

Cross-user only when the identity directory is attacker-writable — possible because CLAUDE_CONFIG_DIR is taken verbatim and can point at a shared location. There, another user pre-plants .claude.json.perch-tmp as a symlink and Perch writes the identity JSON through it to a file of the attacker's choice.

Solution

Unlink the temp path and create it with create_new(true) (the shape create_private_file already uses).

Effect

Removes the symlink-follow; a stale temp from a killed process now fails loudly instead of being reused.

L5 Low bug remove reports the credential deleted when the store never held it

src/credentials.rs:142-150 · src/commands/remove.rs:336-338
Cause

forget treats keychain exit 44 (NotFound) as success, and remove then states flatly "the Credential Perch held for it is deleted". The keychain account name is $USER; if that differs from when the credential was written (login rename, sudo -u, a CI/launchd context, or USER unset in one shell), the delete is a no-op that reads as success.

Explanation

The plaintext copy and profile dir are deleted, so the user can't notice — while the macOS keychain retains a working credential for an account the tool just said it destroyed.

Solution

Have forget report whether it removed anything, and word remove's message conditionally — distinguishing "the other store was legitimately empty" from "nothing was found to delete".

Effect

The success message stops overclaiming; a stranded credential becomes visible.

L6 Low security No fsync — a crash can zero .claude.json or lose a rotated refresh token

src/host/real.rs:181, 512-518 · src/host/mod.rs:275-276
Cause

Every write-and-rename skips File::sync_all and a parent-directory fsync. rename is atomic against other processes, not against a crash: on power loss the rename can be durable while the data blocks are not, leaving a zero-length ~/.claude.json or a truncated .credentials.json.

Explanation

Sharper here than usual because observe::renew_under_the_lock stores a credential Anthropic has already rotated — a lost write is Quarantine::RotationLost, unrecoverable except by a fresh login.

Solution

sync_all the temp file before the rename in create_private_file and write_atomically, then fsync the parent dir.

Effect

Two extra syncs per credential write / switch — negligible on SSD — in exchange for crash durability of the one write that can't be retried.

L7 Low security Lock loss is unobserved and release deletes whatever is at the path

src/lock.rs:48-70, 160-165
Cause

A lock artifact carries no holder identity (a bare directory, matching Claude Code). So: (a) a failed touch in renew means the lock is gone and someone else may hold it, but the write proceeds anyway; (b) release then remove_dir_alls the path unconditionally, deleting the new holder's lock; (c) abandoned returns true when the mtime can't be read at all, licensing a takeover of a live lock on a stat error.

Explanation

Not attacker-driven — needs a stall longer than the 60 s staleness window, which the code itself notes a permission-prompting keychain can cause.

Solution

Write a holder token (pid + start time, already exposed by the Host) into the lock dir; verify it before release and before proceeding past a failed renew; treat an unreadable mtime as "held". A token file inside the directory stays compatible with Claude Code's bare-mkdir protocol.

Effect

Lock loss becomes detectable and stops cascading. Small divergence from Claude Code's scheme to watch as it drifts.

L8 Low bug add's Group prompt validates shape only, then aborts after the login on an alias collision

src/commands/add.rs:176-199, 57
Cause

The re-ask loop validates the answer with validate_name only; the refuse_taken_names check runs after the loop. If the answer collides with an existing Alias, validate_name passes, the loop exits, and refuse_taken_names then raises Conflict — aborting the command after the browser login was already spent and discarded.

Explanation

The loop's own comment says "losing the Account over a typo would be a poor trade" — which is exactly what happens for the collision case it doesn't check.

Solution

Run registry.refuse_taken_names(alias, Some(name)) inside the loop and re-ask on Err.

Effect

A colliding group name is re-prompted instead of wasting the login.

L9 Low bug remove's confirmation for the last non-active account describes a state that isn't true

src/commands/remove.rs:203-233
Cause

When is_active == false and remaining == 0 but active == None, the successor: None branch prints "Claude Code goes on running as {account} — the live Credential is not Perch's to take away" — false: that account isn't active and the live store may hold nothing or someone else's credential. The user is asked to agree to a description of a state that isn't theirs.

Solution

Branch the None-successor sentence on consequence.is_active.

Effect

The confirmation stops asserting an untrue live state.

L10 Low bug Minor prose/state mismatches

src/cycle.rs:430-446 · src/commands/status.rs:74-83
Detail
  • cycle::nobody_is_a_candidate counts an account that is both disabled and quarantined in both tallies, so the reported counts can exceed the number of accounts.
  • status with accounts held but active == None says "run claude and log in", where perch switch <target> is the actual remedy (the one remove itself recommends).
  • claude_version takes the first stdout token unconditionally, so "error: …" yields version "error:" in refusal messages; a cached used_percent of -5.0 renders "105% headroom". Both cosmetic; a clamp + guard is a few lines.

Messages match reality; no functional risk.

Simplifications & dependencies

The project has explicit ADR positions on dependencies (ADR 0008 keychain, ADR 0021 platform primitives), and most crate-vs-hand-rolled calls are deliberate and correct. These are the ones worth acting on, plus an honest account of the crate swaps that would not help.

D1 Simplify ratatui + crossterm are declared but used nowhere

Cargo.toml:13-14
Finding

A recursive grep over src/ and tests/ finds zero references to either crate — the only hits are the Cargo.toml lines themselves (a TUI is a future plan noted in utilization.rs, not present code). Together they are the largest subtree in the dependency graph, compiled and audited for nothing.

Effect / tradeoff

Faster clean builds, smaller Cargo.lock surface, fewer CI minutes across the 3-OS matrix. Note: the Cargo.toml comment justifies declaring libc/windows-sys partly by "already pulled in by crossterm and ratatui" — but chrono alone still pulls both transitively, so the "adds no crate" claim survives a one-line comment edit. Adding cargo machete to CI keeps this class of drift out permanently.

D2 Simplify color-eyre is pulled in for a panic hook only

src/report.rs:12-21
Finding

The sole use installs color-eyre's panic hook and explicitly discards its error hook; error.rs is the real error story and never touches eyre. color-eyre drags in eyre, backtrace, owo-colors, indenter for one pretty panic message.

Solution

A hand-rolled std::panic::set_hook printing payload + location + version + issues URL is ~15 lines with zero deps; human-panic is a much smaller crate that does exactly this.

Effect / tradeoff

Drops 5-8 transitive crates. You lose color-eyre's span-formatted backtrace, which is genuinely nicer for bug reports — so if report quality is the point (the module says it is), keeping it is defensible. Worth a deliberate re-decision once D1 removes its neighbours.

D3 Crates Crate-vs-hand-rolled: what helps, what correctly conflicts with the ADRs

Worth adopting
  • tempfile (NamedTempFile::persist) — replaces the fixed .perch-tmp suffix in write_atomically, which two concurrent processes collide on and which enables the L4 symlink issue. Randomised temp names fix both.
Correctly hand-rolled — do not swap
  • keyring — rejected by ADR 0008 for a real reason: macOS anchors a keychain item's ACL to the creating binary, so Perch must drive the same security binary Claude Code does. The wrapper honours all four documented CLI constraints.
  • sysinfo — ADR 0021 chose vetted libc/windows-sys declarations over a heavy process-table crate; the /proc parsing is careful (rsplit on ) for hostile comm names).
  • which / dirs / fd-lock / fs4 — each conflicts with the Host-port abstraction (which lets FakeHost test Windows .cmd and unset-HOME cases on any OS) or with the fact that lock.rs takes Claude Code's directory locks, not locks of its own. A file-lock crate would lock against nobody.
  • reqwest/ureq — the curl-via-stdin design is what keeps the access token out of argv; ADR 0021 covers it. std::io::IsTerminal is already used instead of a terminal-detection crate.
  • serde_json value surgery — the hand-rolled byte-preserving splicer in json.rs is justified: no format-preserving JSON editor exists in Rust, and round-tripping would reorder a file Perch doesn't own.

D4 Simplify Duplicated logic worth unifying

Findings
  • quote() / quoted() — byte-for-byte identical escaping in keychain.rs:102 and host/real.rs:81. Two copies is how one gets fixed and the other doesn't.
  • Process spawn + Execution build — the same spawn-with-optional-stdin dance and Execution { status: code().unwrap_or(-1), stdout: from_utf8_lossy… } appears in curl, run_security, and exec. One impl From<Output> for Execution + one exec_with_stdin removes ~35 lines.
  • tmp-file-beside-and-rename — write_atomically and write_private_file share the whole choreography; a replace_via_tmp(path, write_fn) collapses it and stops the failure-cleanup drifting between the secret and non-secret paths.
  • Mirror enums — main.rs defines ConfigAction/GroupAction + From impls that mirror ConfigCommand/GroupCommand field-for-field (~70 lines). clap is already an unconditional dep, so deriving Subcommand directly would delete them (tradeoff: the lib picks up a clap derive).
  • Two Scope enums — cycle.rs and commands/list.rs both define Scope with near-identical accounts() dispatch. Unifying is ~25 lines; the counter-argument (cycle deliberately has no Everything) is real — decide it explicitly rather than by accident.
  • std::io::Error::other(err.to_string()) laundering repeated at 6 sites — PerchError::file_read/file_write constructors remove ~20 lines.
Effect

~150 lines removed across behaviour-preserving refactors; each de-duplication closes a "fix one copy, miss the other" hazard.

D5 Cargo / CI Hygiene gaps

Findings
  • No [lints] table — CI enforces clippy -D warnings but local cargo clippy doesn't. Add [lints.clippy] all = "deny" and [lints.rust] unsafe_op_in_unsafe_fn = "deny" (there are five unsafe blocks in host/real.rs) so local and CI agree.
  • No [profile.release] — strip = true, lto = "thin", codegen-units = 1 is a free ~30-50% binary-size cut for a distributed CLI.
  • MSRV over-pinned — rust-version = "1.97.1" compares the full triple; "1.97" matches convention (the exact patch belongs in rust-toolchain.toml, where it already is). And it's never checked — add a cargo +1.97 check --locked leg.
  • Missing CI legs — cargo machete (would have caught D1), cargo-audit, and a schedule: trigger so the contract suite catches Claude Code drift on a quiet week (it exists specifically to find drift before users do, against a continuously-updating Claude Code).
Effect

CI is already strong (SHA-pinned actions, persist-credentials: false, least-privilege token, --locked, 3-OS matrix, if: always() gate). These close the remaining drift and reproducibility gaps.

Test quality

The suite is a genuine strength — 236 tests, effect-trace assertions that pin the switch's ordered contract, all four PID-recycling quadrants, network-discipline checks in nearly every suite, and a fake clock that makes timing tests instant. The gaps below are mostly places where the test double can't express the failure the production code guards against, so the guard is effectively unverified.

T1 Tests Seven gaps, most-impactful first

High-impact gaps
  • The read-back guard is untestable. profile::write_and_read_back exists for security's silent stdin truncation, but the fake keychain/filesystem always store bytes faithfully, so the failure branch can never fire — it could be deleted and no test would fail. Fix: add FakeHost::with_keychain_truncating_after(n) / with_file_corrupting_writes and assert the switch stops at the write step.
  • The fake keychain works off-macOS, where real Linux/Windows has no /usr/bin/security. tests/storing.rs's "second-choice store" test passes only because of this — on real Linux that scenario fails outright. Fix: make FakeHost::keychain_* return Unavailable when platform() != MacOs unless a test opts in, then re-scope the storing test.
  • Slug edge cases untested — the empty-slug delete (H5) and the add slug-collision (H4) have no test pinning a refusal. Fix: a_slug_is_never_empty… (unit) and adding_an_account_whose_email_slugs_to_an_existing_profile_is_refused (behaviour).
Medium-impact gaps
  • Registry-save failure after the destructive step is never exercised (remove post-delete, switch record_active) though the fake supports with_unwritable_file(REGISTRY_PATH) — these are the exact windows H2 is about.
  • The under-lock re-read (observe.rs re-checking liveness/credential inside the lock, the whole ADR 0006 safety argument) can't be tested — the fake can't mutate the world during a sleep/lock-wait. Fix: add FakeHost::on_sleep(callback).
  • credentials::read swallowing a fallback error (M6) is undecided and untested — one line of with_unreadable_file arrangement pins it either way.
  • No concurrency test for the lock and no property tests for ranking. The mkdir-exclusivity claim is the entire lock protocol but is only checked sequentially; cycle.rs's tier invariants are example-based, so a comparator sign-flip confined to SoonestReset could survive. Fix: an 8-thread lock::under race test on RealHost, and proptest properties (winner ≥ every candidate; exhausted/disabled/quarantined never chosen; determinism).
Also worth noting
  • Dead error branches the fake can't reach: remove_file/remove_dir_all/create_dir_all never fail in FakeHost, so credentials.rs:151-157, lock.rs:101-108, and the remove forget-failure path are untested.
  • Unicode name matching is ASCII-only (eq_ignore_ascii_case) while validate_name accepts Unicode — café/CAFÉ are different names. Pin the intended rule.
  • A 1100 ms real sleep runs in every cargo test (real.rs:846) — belongs in the contract suite. A contract keychain test leaves a real login-keychain item behind if an assertion panics mid-test — use a drop guard.

Verified clean

Areas actively checked and found correct — recorded so the report's silence elsewhere isn't mistaken for "not looked at".

  • argv secrecy on the HTTP path — curl driven via --config - with URL/headers/body all on stdin; both binaries invoked by absolute path; Windows curl from %SystemRoot%, never a PATH walk.
  • No shell is ever spawned — every exec is Command::new with an args array; no sh -c, no string concatenation.
  • No secret in any error, log, or stdout — Credential's Display is <credential N bytes>; anthropic::understand discards reply bodies; parse errors carry position only.
  • Path traversal via email is blocked — slug maps every non-alphanumeric to - (the empty case is H5, a different bug).
  • Capture-before-write ordering and interruption recording — the switch state machine records incoming_is_live on failure, and the retry self-captures correctly.
  • Credential files 0600 / dirs 0700 at creation (not chmod'd after), write→read-back→supersede in both directions, loose-file tightening said once.
  • Session-marker corroboration (ADR 0022) — recycled-PID reasoning is exact, not heuristic; an unreadable start time is a refusal, not a guess.
  • The JSON splicer is depth- and escape-aware and rejects truncated/non-object values (only defect: the L3 indentation panic).
  • Registry version-from-the-future is refused; the v2→v3 quarantine migration fails safe.
  • Ranking/cycling math — worst-window selection, four-tier ordering, negated-timestamp trick, stable-sort tie handling, and honest non-outcomes are all correct; units (millis vs seconds, /proc field 22, FILETIME epoch) are right throughout and all times are UTC.
  • No export/import crypto exists yet (ADR 0014 is unimplemented), so there was none to review.
